# AI 课程资料粒度与检索调整方案

核查日期：2026-10-11。方案已实施并部署。下文“当前策略”保留修改前的核查记录，实际配置和验证结果见 [实施结果](course-material-granularity-results.md)。旧资料分组采用本机主题规则和已有索引，不向外部模型发送原资料。

## 1. 当前策略与实际数据

资料文件和检索片段是两层结构，不能用一个 chunk_size 参数同时解决。

| 层次 | 当前行为与运行参数 |
| --- | --- |
| 联网搜索 | 每批先调用一次 web_study，工具 max_uses=1，再调用一次结构化整理模型；不是每份文件分别联网搜索 |
| 文件组织 | 搜索提示要求最多 limit 个不同知识点；整理提示要求每份正文约 200～400 字，一个返回项保存为一个 Markdown 文件 |
| 生成数量 | 默认最多 10 份，硬上限 10；允许实际生成更少 |
| 正文校验 | GeneratedMaterial.content 为 1～3000 字符；没有最小有效内容或主题完整度校验 |
| 模型输出 | 实际 llm_max_completion_tokens=4096，单次请求超时 60 秒；搜索及整理共同使用当前配置 |
| 解析 | Markdown 按每个标题拆 section；TXT 无标题拆分；DOCX 按段落或表格；PDF 按页。不同 section 不合并 |
| 检索切片 | chunk_size=1000 字符，chunk_overlap=150 字符；长 section 在后半段优先寻找换行边界，否则按字符截断。重叠只发生在同一 section 内；短 section 原样单独入库 |
| 来源 | 文末“网页来源”是独立标题，所以纯链接列表也独立生成向量与关键词索引 |
| 入库 | 每份文件单独导入，文件内每 16 个片段一批调用嵌入模型；没有跨文件合并嵌入请求 |
| 问答检索 | hybrid；向量候选 20、BM25 候选 20；RRF 融合常数 60，最终前 5 个片段 |
| 上下文 | 总预算 7000 字符，单片段另外硬截到 1000 字符；标题、文件名也占预算 |

本机数据库只读统计：当前有效 AI 资料 15 份，全部已发布；共有 30 个片段，其中正文 15 个、纯网页来源 15 个。正文片段最短 153 字符、中位数 200 字符、最长 256 字符，全部少于 400 字符。长度包含资料中的参考提示，不等同于净正文长度。

证据位置：`app/providers.py` 的 `course_materials`，`app/campus_schemas.py` 的 `GeneratedMaterial` / `MaterialSearchInput`，`app/parsing.py` 的 `parse` / `chunk_sections`，`app/jobs.py` 的 `process_import`，`app/retrieval.py` 的 `retrieve_with_vector`，`app/config.py` 的 `Settings`。

## 2. 原因与影响

首要原因是提示词主动把每个小知识点做成单独文件，且要求很短。每份正文还未达到 1000 字符就已结束，调大 chunk_size 不会把多个文件合并，也不会自动增加资料的完整度。

其次，按标题无条件拆 section，且不合并短段。更完整的文档如果增加很多小标题，仍可能产生大量只有一两句的检索片段。单纯增加每份正文长度也不足以解决入库碎片化。

纯来源片段占当前片段数的一半，增加嵌入及索引工作，也可能进入前 5 个候选，挤占解释知识的上下文。短正文使一次检索容易只得到零散定义，缺少背景、关联和示例。

生成速度不能仅由文件数量解释：现有流程已经共享一次联网搜索，瓶颈还可能包含模型响应、多个文件独立导入、嵌入调用、以及发布时更新全局知识库 generation。混合检索缓存未命中时，会加载可见片段并建立 BM25；每份发布引发 generation 变化可能增加重建次数。这些是代码支持的影响路径，尚未对本次用户体验做耗时分阶段实测，不能给出确定的提速比例。

## 3. 推荐参数及组织方案

| 项目 | 推荐首轮配置 | 修改意图 |
| --- | --- | --- |
| 文件单位 | 一个完整主题或章节，一份包含若干相关知识点 | 减少维护项，保留内部二、三级标题 |
| 默认生成份数 | 10 → 3，单次硬上限仍为 10 | 保留用户此前的上限要求，避免默认请求十份浅资料 |
| 每份正文目标 | 200～400 → 800～1600 中文字左右 | 包含概念、关系、机制、示例、易错点；按网页依据选用结构 |
| 正文长度硬上限 | 保持 3000 字符 | 不先扩大单份上限，控制详情阅读与模型输出成本 |
| 单次整理批次 | 最多 3 份；用户要求更多时分批处理，最多存入 10 份 | 防止一次输出十份长资料导致截断，并逐批展示进度 |
| 资料整理输出额度 | 专用上限先设 8192 tokens/批；按实际完整输出与耗时再调 | 不改普通问答的 4096，也不假设字符数等于 token 数 |
| 联网搜索工具次数 | 首轮保持 1；依据不足时才追加，整次任务上限 2 | 共享检索依据，避免机械增加搜索次数；追加前有数量及时间预算 |
| 检索片段目标 | 约 800～1000 字符 | 检索单位仍小于章节文件，不把整篇文档作为一个向量 |
| 检索片段硬上限 | 1000 → 1200 字符 | 给完整段落、例子留空间 |
| 短片段合并阈值 | 新增 300 字符 | 同一父章节下，相邻短小节合并，合并后不超过 1200；跨独立主题、表格、代码块不机械拼接 |
| 重叠长度 | 150 → 120 字符 | 只用于必须拆开的长段；优先完整句段重叠，不对自然短小节强加重复 |
| 来源及参考提示 | 留在展示原文与来源元数据中，不单独参与正文向量/BM25 | 避免纯链接及重复免责声明占召回名额 |
| 候选召回 | 向量 20、BM25 20、RRF 60 暂时保持 | 先验证组织与切分，减少同时调整的变量 |
| 最终片段数 | 5 → 6，重叠内容去重 | 增加主题覆盖，避免同一内容重复占位 |
| 单片段上下文上限 | 1000 → 1200 字符 | 和新切片上限一致，避免召回后再次截断正文 |
| 总上下文预算 | 7000 → 8000 字符，包含标题、文件名 | 为六个片段及引用元数据留预算；实际仍按预算裁剪 |

上述是起始配置，不是已证实最优值。若网页只能支持一段解释，应少生成、跳过或提示依据不足，不凑份数，也不以空话补足字数。针对单一窄主题，允许只生成一份；“3 份”是默认上限。

例如“包、访问修饰符、静态成员、内部类”可以在主题相关且网页依据充分时组织成“Java 类的组织与访问控制”一份资料，内部再分小节；“JDBC”不为凑长度并入这份。需要按课程结构判断边界，不能简单把所有旧文件拼成一篇。

切分时保留每个子节的标题路径和原文范围；合并后引用必须仍能定位来源。Markdown 解析需要识别代码围栏，避免将代码内的 `#` 当标题；表格和代码优先整体保存，超长时另设可追踪的拆分规则。

## 4. 效率及旧资料处理

先调整生成提示和主题规划，再调整解析切分及来源索引过滤，最后修改问答上下文参数。主题规划要比较已有资料覆盖范围，避免只依赖完全相同的文件名；跨批次也不得重复拆出已有小知识点。

多份资料继续共享已有搜索摘要及来源，额外搜索只补证据缺口。较长正文会增加模型输出时间，所以用默认 3 份、分批返回和渐进进度控制等待；不能承诺变长后单次请求一定更快。嵌入可跨同批文件收集到最多 16 个片段再发送，仍保留各文件独立的发布与失败状态。

旧资料不会因为改参数而自动合并。建议提供按主题整理的迁移预览：列出旧文件与拟合并新文件，先生成新版本并完成索引、验证引用，然后切换展示；原资料保留可回退状态，历史引用不直接删除。旧资料重组应以原文为输入进行去重与编排，不再次凭空补充知识。

目前 index_key 只有嵌入模型身份，没有切分策略版本，而且相同文件哈希与 index_key 会复用已有版本。重建必须记录独立的切分策略版本并调整版本复用判定；检索兼容性仍以嵌入模型为准，允许迁移中旧、新切分版本共存。不要直接修改全局 index_key 后让旧资料全部退出检索。

## 5. 验收方法

1. 以现有 Java 资料及固定查询作为基线，标注相关章节，记录合并前后文件数、正文长度、短片段比例、纯来源片段数及总片段数。不能仅以文件变少判断知识覆盖是否保持。
2. 检查多知识点问题和单知识点问题：章节结构完整、示例及引用可追踪，代码和表格没有截断；来源链接仍可在详情展开。
3. 标注相关证据片段，比较 Recall@6、首条相关结果排名、回答正确性和引用完整性；并检测纯来源片段进入召回的情况，新方案应为零。必须与相同查询、相同嵌入模型及同一资料内容版本比较。
4. 分开记录搜索、结构化整理、嵌入、检索、首次可见和整批完成耗时，以及调用数和 token 使用量。比较中位数及较慢请求，不给未经实测的提速承诺。
5. 验证同主题跨批去重、最多十份、长输出截断拒收、部分失败恢复、旧版本回退、历史引用，以及生成/导入期间删除课程不能重新发布资料。
